# 상승 금지 충돌 회피 정책 (1 m급 기체) — ONNX 배포 메뉴얼

이 폴더를 받아 ROS 2 패키지에 붙이는 사람·에이전트를 위한 문서입니다.
정책은 전처리된 LiDAR 거리 이미지와 전역 경로를 받아 **WP 1개와 속도 명령**을 20 Hz로 냅니다.
장애물은 **옆으로만** 피하고, WP를 전역 경로 고도 위로 올리지 않습니다.

만든 날: 2026-10-08. 원본: `drone_wp_rl` (Isaac Lab + skrl PPO), 과제 `v3big`.

## 2. ONNX 그래프

- 입력 `obs`: float32 `(N, 216)` — **정규화하지 않은** 관측. 정규화(평균·표준편차, ±5 클립)는 그래프 안에 있습니다.
- 출력 `action`: float32 `(N, 3)` — `[방위 오프셋, 고도 오프셋, 속도]`, 각각 [-1, 1]로 이미 클립됨.
- 구조: 216 → 512 → 256 → 128 (ELU) → 3. opset 17, 배치 축 가변. CPU에서 충분합니다.
- 출력은 학습 평가와 같은 결정적 출력(분포의 평균)입니다. PyTorch 원본과의 차이는 최대 2e-6.

## 3. ONNX 밖에서 구현해야 하는 것

그래프는 망만 담고 있습니다. 아래 네 가지는 호출하는 쪽 책임이고, 전부 `ca_policy_ref.py`에 들어 있습니다.

1. **관측 216개 만들기** (4절)
2. **출력을 WP와 속도로 바꾸기** (6절) — 상승 금지는 여기서 지켜집니다
3. **속도 조절기** (7절) — 학습 때 정책 밖 환경에 있던 규칙이라 배포 쪽에도 있어야 합니다
4. **상태 유지**: 직전 행동, 지나온 경로 구간 번호, 정체 타이머 (새 경로를 받으면 초기화)

가장 쉬운 방법은 참조 구현을 그대로 쓰는 것입니다.

```python
from ca_policy_ref import NoClimbPolicy
pol = NoClimbPolicy("ca_noclimb_tau05-12.onnx", "cfg.json", path_xy, path_z)   # 전역 경로 (K,2), (K,)
out = pol.step(pos, vel, R_wb, points=pts, density=0.0)                        # 20 Hz 마다
wp_enu, speed = out["wp"], out["speed"]
```

## 4. 관측 (216차원, 순서대로)

좌표계: 월드 = **ENU** (x 동, y 북, z 위), 기체 = **FLU** (x 앞, y 왼쪽, z 위). PX4의 NED/FRD는 변환해서 넣습니다.
"기준 방위"는 현재 위치에서 **경로 위 2.5 m 앞 점**을 향하는 수평 방향입니다 (기체 기수 방향이 아님).

| 인덱스 | 내용 | 정규화 |
|---|---|---|
| 0 | 속력 (3D) | ÷ 5 |
| 1:4 | 기체 프레임 속도 | ÷ 5 |
| 4:7 | 경로 2.5 m 앞 점(경로 고도)을 향하는 단위벡터, 기체 프레임 | — |
| 7:10 | 기준 방위 프레임 속도 [전방, 좌측, 수직] | ÷ 5 |
| 10 | 남은 경로 길이 R | tanh(R / 10) |
| 11 | 횡오차 (+ = 경로 왼쪽) | ÷ 6, ±1 클립 |
| 12 | 고도 편차 = 현재 고도 − 현재 위치의 경로 고도 | ÷ 4, ±1 클립 |
| 13 | 2.5 m 앞 점에서의 경로 방향 − 기준 방위 | ÷ π |
| 14 | 지면 기준 고도 | ÷ 10, [0, 1] 클립 |
| 15:207 | 거리 이미지 6 × 32 (5절) | ÷ 10, [0, 1] 클립 |
| 207 | 주변 장애물 밀집도 (아래 주의) | [0, 1] |
| 208:211 | 기체 프레임 중력 방향 = R_wbᵀ · (0, 0, −1) | — |
| 211:214 | 직전 스텝의 행동 (클립된 값, 처음에는 0) | — |
| 214 | 정체 타이머: 남은 거리가 1 m 넘게 줄지 않은 시간 | ÷ 4 s, [0, 1] |
| 215 | 타이머를 0으로 되돌리려면 더 가야 하는 거리 | ÷ 1 m, [0, 1] |

- **경로 투영**: 현재 위치를 전역 경로(수평 꺾은선)에 투영해 호길이 `s`를 구합니다. 지나온 구간 뒤로는 찾지 않습니다(현재 구간부터 두 구간 앞까지만). 경로 고도는 웨이포인트 사이를 선형 보간합니다.
- **정체 항(214, 215)**: 남은 거리가 지금까지의 최소값보다 1 m 넘게 줄면 타이머 0, 아니면 매 스텝 0.05 s 증가. 학습에서는 4 s를 넘으면 실패로 끝냈습니다.
- **밀집도(207) 주의**: 학습에서는 "표면까지 4 m 안에 있는 장애물 개수 ÷ 4"를 **시뮬레이터의 참값**으로 넣었습니다. 실제 센서에서 이 값을 어떻게 만들지는 정해지지 않았고, 값이 틀릴 때 정책이 얼마나 민감한지도 측정하지 않았습니다. 점군을 물체 단위로 묶어 4 m 안의 물체 수를 세는 것이 정의에 가장 가깝습니다.

## 5. 거리 이미지 (6 × 32)

- **고도 칸 6개**: −7° ~ +52° (Mid-360 시야)를 6등분. 한 칸 약 9.83°. 0번이 가장 아래.
- **방위 칸 32개**: 한 칸 11.25°. **0번 칸의 중심이 기준 방위**이고 반시계(왼쪽)로 증가합니다. 0번 칸은 기준 방위 ±5.625°.
- **값**: 그 칸에서 가장 가까운 반사점까지의 거리 [m]. 빈 칸과 10 m 이상은 10.
- **펼치는 순서**: 고도 칸 우선. 관측 인덱스 = 15 + 고도칸 × 32 + 방위칸.
- **각도 기준은 월드 수평면**입니다. 점군을 기체 자세(롤·피치)로 보정해 월드 축 방향으로 돌린 뒤 칸에 넣어야 합니다. 기체 기준 각도를 그대로 쓰면 안 됩니다.
- 지면 반사도 포함됩니다(학습 이미지에 지면이 있었음). 기체 자신의 반사는 걸러야 합니다.

`ca_policy_ref.pointcloud_to_image(points, ref_bearing, cfg)`가 이 규칙대로 만듭니다. `points`는 기체 기준 상대 위치이고 축은 월드(ENU) 방향입니다.

## 6. 출력 → WP와 속도

행동 `a = [a0, a1, a2]` (각각 [-1, 1]):

- **방위**: `azim = 기준 방위 + a0 × 90°`
- **WP 수평 위치**: 현재 위치에서 `azim` 방향으로 3 m
- **WP 고도**: `경로 3 m 앞의 고도 + dz`, 여기서 `dz = a1 × 0` (a1 ≥ 0) 또는 `a1 × 0.2 m` (a1 < 0). 결과를 [0.7, 9.5] m로 클립
- **속도**: `0.5 × (a2 + 1) × 5 m/s` — 수평 속도 명령

**상승 금지는 `wp_alt_up = 0`으로 지켜집니다. 망 자체는 a1 > 0을 낼 수 있으므로, 이 값을 0이 아닌 수로 바꾸면 같은 정책이 위로 올라갑니다.** `cfg.json`의 `wp_alt_up`을 건드리지 마세요.

WP는 매 스텝 새로 만들어집니다(항상 3 m 앞). 사실상 "방향 + 고도 + 속도" 명령입니다.

경로가 오르막이면 WP도 경로를 따라 올라갑니다. 이것은 회피 상승이 아니라 경로 추종입니다.

## 7. 속도 조절기

정책 속도 명령에 상한을 겁니다. `d` = 거리 이미지의 최소값 [m]:

```
v_cap = clip(2.0 × (d − 0.8) + 0.6,  0.6,  5.0)
speed = min(정책 속도, v_cap)
```

가장 가까운 물체가 0.8 m 이내면 0.6 m/s까지 낮아집니다. 정책은 이 규칙이 있는 상태로 학습했으므로, 빼면 장애물 근처에서 학습 때보다 빠르게 날게 됩니다.

## 8. 한 스텝의 순서 (20 Hz)

1. 위치·속도·자세를 ENU/FLU로 받는다
2. 경로에 투영해 `s`, 기준 방위, 횡오차, 고도 편차를 구한다
3. 정체 타이머를 갱신한다
4. 점군을 기준 방위 기준의 6 × 32 거리 이미지로 만든다
5. 관측 216개를 조립해 ONNX를 돌린다
6. 행동을 WP·속도로 바꾸고 속도 조절기를 적용한다
7. 행동을 "직전 행동"으로 저장하고 WP·속도를 내보낸다

목표 근처 처리는 학습에 없었습니다(목표 0.5 m 안에 들어오면 에피소드 종료). 남은 거리가 3 m 안쪽이면 WP를 목표점으로 바꾸는 식의 전환을 호출하는 쪽에서 넣는 것을 권합니다.

## 9. 학습 때의 가정 (배포 환경이 이와 다르면 성능이 달라집니다)

- **추종기**: 수평 속도 명령 = `속도 × (WP 쪽 수평 단위벡터)`, 수직 속도 = `3 × (WP 고도 − 현재 고도)`를 ±1.5 m/s로 클립. 둘 다 1차 지연(정책 이름의 범위)과 명령 지연 0~100 ms를 거칩니다.
- **속도**: 수평 최대 5 m/s, 수직 최대 1.5 m/s.
- **기체 크기**: 기체 중심이 장애물 표면에서 0.6 m 안에 들어가면 충돌(프로펠러 끝 반경 0.5 m + 여유 0.1 m).
- **고도**: 비행 허용 범위 0.5~10 m. 전역 경로 고도는 약 0.9~8 m, 경사 최대 약 15°.
- **센서**: Mid-360을 똑바로 장착했다고 보고 고도각 −7°~+52°, 최대 10 m. 시뮬레이터의 해석적 센서로 학습했고 잡음·누락·운동 왜곡은 넣지 않았습니다.
- **동역학**: 시뮬레이션 기체는 Isaac Lab의 Crazyflie이고, "1 m급"은 충돌 반경과 응답 지연으로만 반영했습니다.

## 10. 성능 (시뮬레이션, 참고)

완화 숲(1 m급 기체에 맞춘 밀도) 벤치마크, 레벨당 1,024개 장면, 60 s 제한, 검증용 시드. L0 → L4는 숲 밀도 낮음 → 높음.

| 정책 | 도달률 L0 / L1 / L2 / L3 / L4 | 충돌률 L0 / L1 / L2 / L3 / L4 |
|---|---|---|
| `tau03-08` | 0.95 / 0.87 / 0.72 / 0.65 / 0.51 | 0.03 / 0.09 / 0.20 / 0.24 / 0.36 |
| `tau05-12` | 0.91 / 0.82 / 0.71 / 0.66 / 0.59 | 0.07 / 0.14 / 0.23 / 0.26 / 0.31 |

- 성긴 숲(L0~L1)에서만 쓸 만한 수준입니다. L2부터는 다섯 번에 한 번 이상 부딪힙니다.
- 2 m 높이 벽을 넘지 못하므로 옆으로 돌아가야 합니다. `tau05-12`는 벽을 돌아가지 못하고 에피소드의 8~10 %에서 들이받습니다(`tau03-08`은 2~4 %).
- 경로 자체가 장애물보다 높게 지나가는 곳에서는 경로 고도 그대로 그 위를 지납니다.

## 11. 검증된 것과 아닌 것

**확인함**
- ONNX 출력 = PyTorch 원본 출력 (최대 차이 2e-6)
- 망 구조는 학습 설정(`rl/skrl_ppo_cfg_v3big.yaml`: 은닉층 ELU, 출력층 활성화 없음, 행동 [-1, 1] 클립)과 대조해 확인
- 참조 구현의 관측·WP·속도 = 학습 환경의 계산 (약 6,000 스텝 비교, 최대 차이 1e-5 수준)
- 참조 구현의 점군 → 이미지 칸 배치 = 학습의 광선 배치
- 위 성능 수치의 평가 경로 = 이 ONNX의 결정적 출력

**확인하지 않음**
- 실제 Mid-360 점군으로 만든 이미지에서의 동작 (학습은 해석적 센서)
- 밀집도(관측 207)를 센서에서 추정했을 때의 영향
- PF + MPPI 추종기와 묶은 비행. 이전 SITL 측정에서 기본 MPPI는 속도 명령을 거의 따르지 못했고(0 → 2 m/s 명령에 10 s 뒤 0.32 m/s), 고도 응답도 학습 가정보다 느렸습니다(±2 m 계단에 63 % 도달 2.1~2.2 s). 추종기 응답이 9절과 크게 다르면 위 성능은 재현되지 않습니다.

## 12. 붙일 때 자주 틀리는 것

- 관측을 미리 정규화해서 넣음 → 그래프 안에서 한 번 더 정규화됨. 원값(표의 스케일만 적용)을 넣을 것
- 거리 이미지의 방위 0번을 기체 기수로 둠 → 기준 방위(경로 2.5 m 앞 점 방향)여야 함
- 점군을 자세 보정 없이 칸에 넣음 → 기울 때 고도 칸이 밀림
- NED/FRD 값을 그대로 넣음 → ENU/FLU로 바꿀 것 (좌측이 +, 위가 +)
- 직전 행동을 0으로 고정 → 매 스텝 갱신할 것
- 속도 조절기를 빼거나 `wp_alt_up`을 바꿈 → 학습 조건과 달라짐
- 20 Hz가 아닌 주기로 호출 → 정체 타이머와 응답 가정이 어긋남
